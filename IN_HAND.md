# In-hand confirmed

The third LockX service connects exact listing photos to a guided mobile camera capture. The seller opens the camera step in their browser, grants camera access, and records one 10-second video. No account, login, or native app is needed to create an inspection, complete capture, read results, publish an approved set, or download marked photos. The browser remembers an anonymous private access key. Each inspection also gets a separate private management link that works on another device. Keep that link: it controls access to the recording, results, and publication. Clearing browser storage removes the local list; the saved management link still works. A capture link cannot manage results or publish photos.

## Run locally

```sh
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python dev_server.py --port 8080
```

Open `http://127.0.0.1:8080/#in-hand`. This preview uses an isolated local identity, stores data in `.lockx-data/preview`, and disables paid analysis and messaging. It is loopback-only: a link containing `127.0.0.1` will not work on a different phone. Never deploy `dev_server.py` or its authentication override.

For actual phones, serve the frontend over HTTPS and point `window.LOCKX_API_BASE` to the deployed `/api/v1` service. The normal backend is `main:app`. Existing vault/recovery routes retain Supabase authentication; In-hand verification uses anonymous browser access and per-inspection management links. Allow the frontend origin in CORS. `LOCKX_DATA_DIR` must be a persistent volume. Set `LOCKX_PUBLIC_APP_ORIGIN` to the canonical website origin before creating QR-marked photos.

## Seller and buyer flow

1. Without signing in, select 1–6 exact listing photos (four is the suggested set), and create a private link. No item name, category, capture-type selection, description, or written details are requested. The initial permission explains that a fully confirmed set automatically receives QR-marked copies and a public verification record; the private camera video is never published. The service compares the photos; the API retains optional metadata fields and explicit publication for older clients. Client-side resizing limits image upload and decode work on phones.
2. On a phone, creation goes straight to the camera step on the same website. On another device, copy or use the Share control to deliver the capture link. Save the separate private management link for later withdrawal or detailed results. This implementation does not send SMS. The capture link expires after 24 hours. Both links keep their secrets in the browser URL fragment; API access uses headers for management keys, which are stored hashed on the server. A management key cannot access another inspection, even if both were created on the same browser.
3. The seller consents and taps Record once. The browser opens the rear camera, starts a server-bound session, then records **one fixed 10-second video**. There are no per-photo holds, stability gates, Next buttons, or live AI waits. A short safe movement instruction asks the seller to show the views and identifying details in the selected photos; appliances remain stationary while the phone moves. Digital tickets retain limited evidence mode.
4. A visible countdown and elapsed timer run independently of camera frame callbacks. Focus and lighting feedback is advisory and cannot extend recording. The 10-second deadline requests recorder shutdown and immediately releases camera tracks. Saving has a separate four-second timeout, including Safari stop-event failure handling. An interrupted or unsaved recording is not presented as verified.
5. Video-only recording (no microphone) uploads in ordered pieces, with idempotent retries and delayed-chunk fallback. The remaining in-memory queue can be retried while the page stays open. The server accepts only a complete decoded fixed-profile clip between 9.5 and 15 seconds, retaining a small browser-timing tolerance around the 10-second client timer. It extracts and preserves evidence across the full short video, then ranks the clearest reference-relevant views plus timeline samples. At most 12 video frames are sent in the final comparison (20 remain stored for a normal 10-second recording), alongside **every selected photo**. Feature matching only selects evidence; it never decides verification. Original frame indices are preserved, and citations to unsent frames cannot support approval. The same phone shows comparison progress and automatically displays every QR-marked photo as soon as the entire set is confirmed and generated. A **Save all to Photos** control hands individual JPEG files to the phone's native share sheet, without a ZIP, report, or Publish step. The files are prefetched before the tap to preserve Safari user activation. The phone requires its own final save choice; browsers cannot silently write into the Photos library. If multi-image file sharing is unavailable, the page provides individual image save/share controls and native long-press instructions. Number/marking readings remain available in details. Capture-token result and download access never grant management, private-video, or publication-control permissions. Upload and AI comparison can take longer than recording. Legacy guided protocols remain compatible but are not used by the new browser flow.
6. The report separates supported photo matches, contradicted evidence, and views that cannot be established. Confirmation requires all selected photos, at least two distinct individual details, supported claims, followed actions, and no flagged evidence problems. Same-model appearance alone is insufficient. Digital tickets cannot earn the physical-item marking.
7. For new inspections with upfront automatic-publication consent, a fully confirmed result immediately generates the exact approved JPEG photo set with a record ID and QR code. The same capture page displays the marked images and **Save all to Photos**; no report, additional checkbox, or Publish step is required. No ZIP is generated or offered by this flow. Native Photos/Gallery save options vary by browser and operating system. Only approved photo copies and the generic photo-set title become public. Originals are preserved privately. Publication never exposes the private recording, owner identity, capture token, or written private details. Older inspections retain their original explicit publication choice.
8. The public record displays the marked photo set and capture time. Withdrawal through the private management link disables the public photos and leaves a withdrawn record at the QR destination. Automatic generation never recreates a withdrawn record. A withdrawn set requires a fresh inspection to publish again.

## Vision configuration and scope

`OPENAI_API_KEY` and a vision model enable final structured comparison and legacy grouped photo planning/advisory prompts. `LOCKX_IN_HAND_VISION_MODEL` overrides the existing `LOCKX_VISION_MODEL`; the existing model is reused when no override is set. Use a model available to your account that supports image input and structured output. In that mode, selected photos, live check frames, extracted video frames, and listing text are sent to OpenAI with `store: false`. No API key reaches the browser. Without configuration or when comparison fails, the result stays inconclusive and cannot be published or marked.

The single final comparison prioritizes legible serial/model numbers, dates, batches, edition numbers, text, and distinctive markings. Readings remain strings, preserving leading zeros. Ambiguous characters (including O/0 and I/1) stay unestablished. Readable unequal values force a mismatch; matching shared model/SKU text alone cannot establish the individual item. Digital-ticket barcode data is excluded from structured identifier output. Selection and model durations are recorded privately for performance checks; fewer image inputs do not guarantee a fixed processing time.

The implementation compares sampled frames; it does not run video-wide forensic analysis or establish a tamper-proof camera origin. Browser timing, randomized actions, media hashes, and rejecting an identical reused recording are useful evidence checks, not protection against every injected stream, edited or re-encoded replay, or synthetic video. There is no LiDAR capture or depth claim.

“LockX In-hand verified” refers to visual correspondence at the recorded time. It is not a certificate of product authenticity, legal ownership, current possession, internal working condition, ticket validity, transfer rights, or shipment. The public record and photo marking must preserve that scope.

## Deployment and validation remaining

This is an initial implementation, not a validated fraud-detection system. Before a public launch:

- Validate genuine and adversarial captures on physical iPhones and Android phones, including Safari/Chrome permissions, supported recording codecs, weak networks, and interrupted uploads. Camera capability is detected in the browser; a fallback explains unsupported browsers.
- Evaluate the configured vision model on known matches, visually identical units, altered listings, unreadable identifiers, replays, and synthetic inputs. The automated tests mock model outputs and do not establish model accuracy. Consider human review for ambiguous or high-value items.
- Move video storage and analysis to an object store and durable job queue for scale. Current SQLite/BLOB storage is intended for one persistent-volume instance; FastAPI background tasks can be interrupted on process exit. Stale automatic-scan decoding jobs are marked inconclusive on later service activity, and abandoned upload pieces are cleaned up. Failed/unavailable comparisons can be retried by the owner; durable recovery for all pending model jobs still needs a job queue.
- Set body-size and concurrency limits at the ingress, redact private capture-token paths from access logs, define retention/deletion and abuse controls, and align the privacy notice with external image processing and optional public publication.
- Add payment/billing and automatic message delivery separately if required. Neither is included here.

## Checks

```sh
.venv/bin/python -m pytest -q
node --check in-hand.js
node --check in-hand-capture.js
node --test test_in_hand_capture.cjs
```

The In-hand tests cover legacy and automatic capture protocols, grouped reference coverage, local quality and motion gates, chunk ordering/idempotency/conflicts/limits, scoped asynchronous follow-ups, real assembled-video decoding, account and anonymous access boundaries, per-inspection management-key isolation, immutable reference access, stage ordering/time limits, session restart, quality warnings, interactive follow-up, real video decoding, replay rejection, conservative result rules, publication consent, actual QR decoding, ZIP downloads, and withdrawal. Browser QA covers photo selection, link creation, seller preflight, responsive layout, and an actual fixed 10-second MediaRecorder round trip with jitter/exposure fluctuations and camera frame callbacks disabled using a local synthetic camera stream. The local-only camera harness is never included in deployed assets. Physical iPhone/Android camera recording and model accuracy have not been established by these tests.
