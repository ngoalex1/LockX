# In-hand verification

LockX connects exact listing photos to a mobile camera capture. The seller opens the camera step in their browser, grants camera access, and records one 10-second video. No account, login, or native app is needed to create an inspection, complete capture, read results, publish approved photos, or download marked photos. The browser remembers an anonymous private access key. Each inspection also gets a separate private management link that works on another device. Keep that link: it controls access to the recording, detailed results, and publication withdrawal. Clearing browser storage removes the local list; the saved management link still works. A capture link never grants management access, private-video access, or withdrawal powers; its limited publication consent path is described below.

## Run locally

```sh
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python dev_server.py --port 8080
```

Open `http://127.0.0.1:8080/#in-hand`. This preview uses an isolated local identity, stores data in `.lockx-data/preview`, and disables paid analysis and messaging. It is loopback-only: a link containing `127.0.0.1` will not work on a different phone. Never deploy `dev_server.py` or its authentication override.

For actual phones, serve the frontend over HTTPS and point `window.LOCKX_API_BASE` to the deployed `/api/v1` service. The normal backend is `main:app`. Existing vault/recovery routes retain Supabase authentication; In-hand verification uses anonymous browser access and per-inspection management links. Allow the frontend origin in CORS. `LOCKX_DATA_DIR` must be a persistent volume. Set `LOCKX_PUBLIC_APP_ORIGIN` to the canonical website origin before creating QR-marked photos.

## Seller and buyer flow

1. Without signing in, select 1–6 exact listing photos (four is the suggested set), and create a private link. No item name, category, capture-type selection, description, or written details are requested. The initial permission explains that individually verified photos automatically receive QR-marked copies and a public verification record, even if other selected photos fail. Unverified photos and the private camera video are never published. The current form sends `auto_publish: true` and `publish_matched_photos: true` with that consent. The service compares the photos; the API retains optional metadata fields and explicit publication for older clients. Client-side resizing limits image upload and decode work on phones.
2. On a phone, creation goes straight to the camera step on the same website. On another device, copy or use the Share control to deliver the capture link. Save the separate private management link for later withdrawal or detailed results. This implementation does not send SMS. The capture link expires after 24 hours. Both links keep their secrets in the browser URL fragment; API access uses headers for management keys, which are stored hashed on the server. A management key cannot access another inspection, even if both were created on the same browser.
3. The seller consents and taps Record once. The browser opens the rear camera, starts a server-bound session, then records **one fixed 10-second video**. There are no per-photo holds, stability gates, Next buttons, or live AI waits. A short safe movement instruction asks the seller to show the views and identifying details in the selected photos; appliances remain stationary while the phone moves. Digital tickets retain limited evidence mode.
4. A visible countdown and elapsed timer run independently of camera frame callbacks. Focus and lighting feedback is advisory and cannot extend recording. The 10-second deadline requests recorder shutdown and immediately releases camera tracks. Saving has a separate four-second timeout, including Safari stop-event failure handling. An interrupted or unsaved recording is not presented as verified.
5. Video-only recording (no microphone) uploads in ordered pieces, with idempotent retries and delayed-chunk fallback. The remaining in-memory queue can be retried while the page stays open. The server accepts only a complete decoded fixed-profile clip between 9.5 and 15 seconds, retaining a small browser-timing tolerance around the 10-second client timer. It extracts and preserves evidence across the full short video, then ranks the clearest reference-relevant views plus timeline samples. At most 12 video frames are sent in the final comparison (20 remain stored for a normal 10-second recording), alongside **every selected photo**. Feature matching only selects evidence; it never decides verification. Original frame indices are preserved, and citations to unsent frames cannot support approval. The same phone shows comparison progress and automatically displays QR-marked copies of the eligible photos once generated. Upload and AI comparison can take longer than recording. Legacy guided protocols remain compatible but are not used by the new browser flow.
6. Each photo has its own outcome: a **green checkmark** for an eligible verified match, a **red X** for a contradicted photo, or a neutral question mark for a view that cannot be established. A finding labeled supported without sufficient verification evidence does not get a green checkmark or a QR marking. For three matches and one failed photo, the page shows all four outcomes and lets the seller save the three verified images. The aggregate result remains `mismatch` or `inconclusive`; partial publication never changes it to `confirmed`. Full confirmation still requires every selected photo. Any eligible subset requires at least two distinct individual details, valid cited evidence, supported claims, followed actions, consistent continuity, and no shared capture or identity concerns. Same-model appearance alone is insufficient. Poor video, incomplete capture, and digital-ticket mode block all physical-item markings.
7. For new inspections with upfront subset-publication consent, each eligible selected photo immediately receives a record ID and QR code. The same page displays marked copies for passed photos and private originals for failed or unclear photos. The **Save photos matched** button sends only the approved JPEGs to the phone's native share sheet; when every photo passes, the button reads **Save all to Photos**. No report, additional checkbox, Publish step, or ZIP is required for this current flow. Files are prefetched before the tap to preserve Safari user activation. The phone requires its own final save choice, such as **Save 3 Images** on iPhone; websites cannot silently write into the Photos library. Native Photos/Gallery save options vary by browser and operating system. If multi-image file sharing is unavailable, the page provides individual image save/share controls and native long-press instructions. Number/marking readings remain available in details. Only approved photo copies and the generic photo-set title become public. Originals are preserved privately. Publication never exposes rejected or unclear originals, the private recording, owner identity, capture token, or written private details. Capture-token result and download access never grant management or private-video permissions.
8. The public record displays only the verified photo subset and capture time, explicitly stating counts such as **3 of 4 selected photos verified**. It never implies the omitted photo passed. Original photo numbering survives omission (for example, Photos 1, 3, and 4); QR links resolve to that exact approved set. Withdrawal through the private management link disables all public images and leaves a withdrawn record at the QR destination. Automatic generation and later consent never recreate a withdrawn record. A withdrawn set requires a fresh inspection to publish again.

## Partial publication and older inspections

`publish_matched_photos` is a strict boolean, defaults to `false`, and is separate from `auto_publish`. Automatic subset publication requires both flags to be `true`. The older `auto_publish` permission promised publication only if every photo matched, so that permission alone never silently publishes a partial set. Full matches retain the original automatic behavior.

For an older opted-in inspection with eligible photos but no subset consent, the seller result returns `publication_status: "consent_required"`. The page explains which matched photos will become public and offers **Prepare matched photos**. That explicit action posts `{ "publish_matched_photos": true, "consent": true }` to `/api/v1/in-hand/seller/{token}/enable-matched-photos`. This narrowly scoped endpoint only works for a previously opted-in inspection with completed eligible evidence. It enables the approved subset without repeating the AI comparison and cannot alter findings, access the private video, or revive a withdrawn record. Older inspections with `auto_publish: false` remain private until their owner explicitly publishes through the private management link.

Seller/private results include `eligible_photo_indices` (original zero-based reference indices), `verified_count`, `total_count`, and `partial`. A ready publication lists only its immutable approved exports, each with its original `photo_index`; public records include the same subset and count metadata. The database stores the selected scope and original-index-to-export mapping atomically. A rendering failure rolls back every generated image and mapping for that attempt, with at most two attempts and no repeated AI call. Invalid or incomplete publication mappings fail closed. Earlier full-set publications without a mapping remain compatible only when the complete approved set is still established. ZIP endpoints remain available for older API clients but are not offered in the phone flow.

## Recording location on verified photos

Verified photo footers optionally include **Video location: City, ST** and identify it as **Device-reported location**. The public QR record displays the same city and state. No name, seller/dealer profile, manual location field, login, or additional product step is required.

The native location permission decision occurs before the camera opens, so its dialog cannot cover the timed recording. When allowed, a fresh device reading is requested during the existing 10-second video. It resolves in parallel through the U.S. Census geocoder, with a bounded lookup and no API key. The current U.S. launch supports incorporated places and Census-designated places; a county alone is not shown as a city. Denied permission, unavailable readings, uncovered areas, and lookup failures leave location off and do not delay recording or verification.

Precise coordinates are transient: they are sent in the request body, rounded to three decimals for the provider lookup, and never written to browser storage, the database, exported images, public records, or application logs. Only city, state, country code, and the device-reported source persist. A fresh, valid location can be added only to its current unfinished recording. Its first resolved city/state is immutable for that session; publication freezes that location together with the approved photos. Rendering and speculative-cache fingerprints include location. A new recording retry requests its own fresh reading. Old completed photos cannot be backfilled, and public records do not establish independently verified GPS, current item location, or identity.

## Vision configuration and scope

`OPENAI_API_KEY` and a vision model enable final structured comparison and legacy grouped photo planning/advisory prompts. `LOCKX_IN_HAND_VISION_MODEL` overrides the existing `LOCKX_VISION_MODEL`; the existing model is reused when no override is set. Use a model available to your account that supports image input and structured output. In that mode, selected photos, live check frames, extracted video frames, and listing text are sent to OpenAI with `store: false`. No API key reaches the browser. Without configuration or when comparison fails, the result stays inconclusive and cannot be published or marked.

The single final comparison prioritizes legible serial/model numbers, dates, batches, edition numbers, text, and distinctive markings. Readings remain strings, preserving leading zeros. Ambiguous characters (including O/0 and I/1) stay unestablished. Readable unequal values force a mismatch and exclude the affected reference from publication; unreadable relevant identifiers leave that reference unverified. Repeated identifiers are checked for each photo where visible, without transferring a number problem to a view that does not show it. Matching shared model/SKU text alone cannot establish the individual item. Digital-ticket barcode data is excluded from structured identifier output. Selection and model durations are recorded privately for performance checks; fewer image inputs do not guarantee a fixed processing time.

The implementation compares sampled frames; it does not run video-wide forensic analysis or establish a tamper-proof camera origin. Browser timing, randomized actions, media hashes, and rejecting an identical reused recording are useful evidence checks, not protection against every injected stream, edited or re-encoded replay, or synthetic video. There is no LiDAR capture or depth claim.

“LockX In-hand verified” refers to visual correspondence at the recorded time. It is not a certificate of product authenticity, legal ownership, current possession, internal working condition, ticket validity, transfer rights, or shipment. The public record and photo marking must preserve that scope.

## Processing speed and lighting retries

Two seconds after recording ends is a performance target, not a verification deadline or an advertised guarantee. The fixed 10-second capture, original image detail, complete-video decoding, final evidence selection, exact identifier comparison, and publication eligibility checks remain required. A slower model response continues processing; it never becomes an automatic pass or a failure merely because two seconds elapsed. Real-device latency and false-accept/false-reject rates still need measurement.

Photo preparation uses at most two concurrent image decoders and preserves selection order. Camera preview and capture-session setup overlap after recording consent. Video chunks continue uploading during capture, and the server prepares the same reference-ranking features ahead of final comparison in a bounded cache keyed by actual content and inspection. This cache only ranks evidence and cannot verify an item. The final AI comparison still receives every selected photo and the selected frames from the complete decoded recording.

QR/JPEG preparation may run privately alongside the final AI call for an opted-in inspection. Running/queued rendering and speculative preparations are bounded process-wide. No public record or marked-media row exists until the final approved subset is known. Rejected images are discarded. Rendering runs outside the SQLite write transaction; publication atomically rechecks the same inspection, session, references, evidence, eligibility, consent, and withdrawal state before committing. Each complete exported JPEG retains its QR-decode validation. Rendering errors cannot change the AI finding or cause a partial database commit.

`GET /api/v1/in-hand/seller/{token}/events` provides a bounded read-only event stream containing only status fields and an opaque revision. Changes trigger an ordinary scoped result fetch immediately; polling remains the fallback. Streams cannot start analysis/publication jobs or reveal the management key, private video, original photos, or detailed model response. Connections have per-inspection and process-wide limits. Each approved JPEG is fetched once and reused as both the displayed image and the native-share `File`; object URLs are revoked on navigation, withdrawal refresh, or page teardown. Server image responses remain non-cacheable.

The first recording uses normal lighting. An optional **Record again with light** action appears only when a completed inconclusive inspection has no verified photos or identifier/photo contradictions and both decoded-video diagnostics and the structured AI finding identify low light or motion blur as the reason. Blur alone is not treated as shakiness; motion advice also requires repeated reliable direction changes. Missing views, item mismatches, different numbers, incomplete recordings, provider failures, and shared integrity problems cannot enable this light-assisted retry.

The retry creates a fresh inspection using the same photos and original consent settings; the failed evidence remains intact. The explicit retry action permits recording to start on the new capture page without another consent click. Server-provided retry eligibility is required; URL parameters cannot enable the light. On a supported rear-camera track, the retry requests light on for the first five seconds, then off for the remaining five. **Light off** disables the cycle if it causes glare. Unsupported, denied, or delayed flashlight controls fall back to normal camera recording, never extend the 10-second timer, and are shut down on stop/cancellation. Flashlight controls are capture aids, not proof of camera origin or authenticity. Physical iPhone/Android flashlight behavior has not been established by synthetic tests.

## Deployment and validation remaining

This is an initial implementation, not a validated fraud-detection system. Before a public launch:

- Validate genuine and adversarial captures on physical iPhones and Android phones, including Safari/Chrome permissions, supported recording codecs, weak networks, and interrupted uploads. Camera capability is detected in the browser; a fallback explains unsupported browsers.
- Evaluate the configured vision model on known matches, visually identical units, altered listings, unreadable identifiers, replays, and synthetic inputs. The automated tests mock model outputs and do not establish model accuracy. Consider human review for ambiguous or high-value items.
- Move video storage and analysis to an object store and durable job queue for scale. Current SQLite/BLOB storage is intended for one persistent-volume instance; FastAPI background tasks can be interrupted on process exit. Stale automatic-scan decoding jobs are marked inconclusive on later service activity, and abandoned upload pieces are cleaned up. Failed/unavailable comparisons can be retried by the owner; durable recovery for all pending model jobs still needs a job queue.
- Set body-size and concurrency limits at the ingress, redact private capture-token paths from access logs, define retention/deletion and abuse controls, and align the privacy notice with external image processing and optional public publication.
- Add payment/billing and automatic message delivery separately if required. Neither is included here.

The In-hand tests cover legacy and automatic capture protocols, grouped reference coverage, local quality and motion gates, chunk ordering/idempotency/conflicts/limits, scoped asynchronous follow-ups, real assembled-video decoding, account and anonymous access boundaries, per-inspection management-key isolation, immutable reference access, stage ordering/time limits, session restart, quality warnings, interactive follow-up, real video decoding, replay rejection, conservative result rules, publication consent, actual QR decoding, ZIP compatibility, and withdrawal. Partial-set regressions cover a three-of-four result, complete-JPEG QR decoding for every passed export, preserved original photo indices, exact-number failures, unclear references, shared evidence blockers, legacy consent restrictions, scoped explicit opt-in, atomic render retries, immutable manifests, and private failed photos/video. Browser QA covers photo selection, link creation, seller preflight, responsive layout, and an actual fixed 10-second MediaRecorder round trip with jitter/exposure fluctuations and camera frame callbacks disabled using a local synthetic camera stream. The local-only camera harness is never included in deployed assets. Physical iPhone/Android camera recording and model accuracy have not been established by these tests.

## Public website

The home page and landing page present only In-hand verification. The public shell uses a responsive system-font design with an illustrated photo/video/QR flow. Home, landing, and former dashboard links open this focused landing page. In-hand capture, private report, and public QR links retain their existing routes. Authentication and recovery data load only for explicit legacy workspace links, so public visitors do not pass through a recovery dashboard or account initialization. The selected-photo form, ten-second recording, AI comparison, automatic QR generation, and native image-save flow remain unchanged.
